# 执行架构：三层分工与派活规约（2026-10-13 实测版）

工作台里的「干活」分三层：**主会话（总管）**、**子代理**、**外部 agent**。本文件定义各层职责、算力归属、派活判断顺序、实测通道命令与验收规约——目标是把重活下沉，总管只做对接、拆解、派单、验收与汇总。

## 1. 三层分工

| 层级 | 本体 | 算力 / 计费 | 职责 | 适合的活 |
|---|---|---|---|---|
| **主会话（总管）** | Hermes 桌面端对话（本机 `deepseek-flash`） | 用户 DeepSeek key | 与用户对接、拆活、派单、验收、汇总汇报 | 需要来回确认的、绑当前会话状态的、3 分钟内的微活、全部验收 |
| **子代理** | 同一 Hermes 运行时的隔离分身（`delegate_task`，并行 ≤10） | 默认继承主会话模型与 key；可钉到本地网关（`wbgateway` / `step-5-preview`，免费） | 独立批量重活：搜集 / 下载 / 扫描 / 审计 / 研究 | 输入输出清晰、可并行、验收标准明确 |
| **外部 agent** | 另一软件本体：Claude Code CLI / dsh 无头 / 六个软件桥 | 各自账号或限免线（本机 claude 本体 = 云知声 U2 Flash 限免） | 代码 / 文件 / 仓库类工程活；能长时间跑的重活 | 交接单能写清的独立任务 |

## 2. 派活判断顺序（实测沉淀）

1. 需要用户来回确认 → 主会话自己做；
2. 绑定当前会话状态（浏览器会话、连续上下文）→ 主会话自己做；
3. 独立、批量、可验收 → 派出去：**代码 / 文件 / 仓库 → Claude Code CLI；搜集 / 下载 / 扫描 / 审计 → 子代理**；
4. 3 分钟内能完的微活（含小修补正）→ 主会话顺手；
5. 无论谁干 → **主会话验收通过后才算完成**（写者 ≠ 验者）。

## 3. 通道 A：Claude Code CLI 派单（已实测）

命令（print 模式；**必须以后台任务运行**）：

```bash
claude -p "$(cat 交接单.txt)" \
  --max-turns 40 \
  --allowedTools "Read,Write,Edit,Bash" \
  --permission-mode auto \
  --verbose > 派单日志.log 2>&1
echo "EXIT=$?" >> 派单日志.log
```

要点（均为本机实测）：

- **必须后台跑**：终端前台调用约 420 秒上限，超时会被打断且丢进度；后台进程 + 日志重定向，完成后收通知再验收。仓库自带封装：`tools/dispatch-claude.sh <交接单.txt> [工作目录] [最大回合数]`。
- **交接单四要素**：背景一段（它看不到你的对话）、任务与硬性要求、验收标准、「不要做 X」清单（不改其它文件、不执行 git 操作）。
- **权限**：`--allowedTools` 预授权工具，**还须 `--permission-mode auto`**；否则命令执行仍被权限系统拦截（被拦时它会如实报告「无法执行」，不会编造结果——实测）。
- **速度基线**：约 27 秒 / 回合（输入约 16 万 token / 回合，云知声 U2 限免线）。任务切分原则：**它负责写，调度方负责完整验收测试**。
- **已知噪音**：stderr 的 `[claude-code:unrecognized_model] … generate_session_title` 是标题子查询，忽略即可。

## 4. 通道 B：子代理（delegate_task）

- 一次可派多路（上限 10），各自独立上下文、并行干活；干完只回收一页总结——省的是主会话上下文，不是算力。
- 适合：多源搜集、批量下载 + 校验、全仓扫描、对比研究。
- 交接单必须自包含；要求可验证产物（绝对路径 + 校验和 / 行数 / 运行输出）。
- 算力默认 = 主会话模型（同一把 key）；要免费化可把 `delegation` 段钉到本地网关（参考 `config/config.yaml` 的 `providers.wbgateway`）。

## 5. 通道 C：六个软件桥（看板卡）

经看板派卡给六个软件智能体（claude-code / deepseek-harness / qoder / trae / trae-solo / workbuddy），每张卡声明执行引擎与证据；见 [`docs/architecture.md`](architecture.md) 与 `docs/agents/`。

## 6. 验收规约（核心）

- 汇报三要素：**谁干 ｜ 算力记谁 ｜ 证据**（可复跑的验证动作与结果）。
- **写者 ≠ 验者**：外部 agent 与子代理的交付物，必须由调度方**实跑或复算**后才算完成——首单实测就靠这步拦下一个必修 bug（见第 7 节）。
- 验收最小集：语法检查 → 实跑主流程 → 边界情形（如 `--help`）→ 敏感信息扫描（用户名 / 密钥 / 邮箱等）。
- 微修补正（< 3 分钟）由调度方直接做，并在汇报中如实记账（谁写、谁修）。

## 7. 首单实录（2026-10-13）：tools/verify-install.py

- **任务**：为复刻者写一键安装自检脚本（六项检查；仅标准库、全中文、PASS / FAIL / SKIP 三态）。
- **派单**：Claude Code CLI（U2 限免线）、后台执行；独立产出 241 行脚本（验收修复后 242 行）。
- **交付方如实报告**：「环境权限拦截命令执行，无法自跑 py_compile；不会编造执行结果」。
- **验收（调度方实跑）**：① 语法检查通过 → ② 实跑崩溃：argparse 帮助字符串里未转义的 `%USERPROFILE%`（`%U` 被当作格式化符），修为 `%%` → ③ 额度守卫检查原定 10 秒超时过紧（实测该探测约 62 秒），放宽到 120 秒 → ④ 六项全部跑通（退出码 0）后入库。
- **沉淀**：弱模型产出必须实跑验收；argparse 帮助字符串里的 `%` 要转义；长耗时子进程单独放宽超时。

## 8. 与看板的关系

看板是「长期自治层」：卡片落库、六软件执行、守护进程看护；本文件是「调度层」：主会话把活分配到三层。两层共用同一条账规——**执行者 / 算力 / 证据三要素**。
